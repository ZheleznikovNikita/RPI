# Интеграционные тесты

Дополнение 13.11.2026: добавлены HTTP-проверки асинхронной отправки, очереди, восстановления состояния и Turbo Frame в `live_game_test.rb`, тесты Connection/GameChannel и настоящие браузерные system tests двух вкладок. Подробная карта и команды находятся в [документе о живых обновлениях](live_updates.md). Указанные ниже исторические числа относятся к предыдущему майлстоуну; браузерные ограничения ниже описывают только HTTP-набор, а не новые system tests.

Майлстоун: подробный Happy Path и 2–3 ответвления от него. Основной сценарий — зарегистрированный игрок проходит игру. Набор также проверяет альтернативный гостевой путь, жизненный цикл сессии и три группы отклонений: неверный ввод, отсутствие прав, ошибка рассказчика.

Проверки выполняются через `ActionDispatch::IntegrationTest`: HTTP-запрос → маршрутизация → контроллер → сервис → модели и тестовая SQLite → HTML/JSON-ответ. Тест проверяет совместную работу этих частей. Он не вызывает метод контроллера напрямую и не подменяет базу данных.

Документ описывает покрытие пользовательских HTTP-сценариев, а не утверждает 100% покрытия всех строк или ветвей кода. Непроверенные области перечислены в конце.

## Как устроен основной сценарий

В `player_journey_test.rb` тест `player registers plays resumes after login finishes and starts a fresh journey` последовательно выполняет следующие шаги в одной cookie-сессии:

1. Открывает меню и форму регистрации, создаёт пользователя. Проверяет запись в БД, переход в профиль и состояние входа.
2. Меняет имя и проверяет новое значение в форме профиля.
3. Из меню начинает игру. Проверяет создание `GameSession` и `Inventory`, пустой инвентарь и подсказку о сохранении.
4. Отправляет команду обычной HTML-формой, включая пробелы по краям. Проверяет переход обратно в игру, нормализованную команду, рассказ и исчезновение подсказки.
5. Проверяет страницы настроек, профиля и UI Kit и ссылки возврата из игрового контекста.
6. Выходит. Статистика становится недоступна без входа. Входит заново тем же аккаунтом и проверяет, что меню предлагает продолжить ту же сессию, а история сохранилась.
7. Отправляет вторую команду через JSON. Проверяет текст, статус и ID сессии в ответе, сохранение обоих действий, успешные запросы и последовательные версии памяти.
8. Завершает игру. Проверяет статус и дату в БД, результат и число действий в статистике. Стрелка после завершения ведёт в меню, при обычном открытии статистики — в профиль.
9. Начинает новую игру. Проверяет новый ID, пустую историю и инвентарь, сохранность завершённой сессии. Выходит и проверяет гостевое меню.

Тест `guest registers from game and starts saved progress without importing transient demo` проверяет другой успешный вход в игру: гостевая команда → регистрация из игрового контекста → собственное сохранённое прохождение. Гостевой демонстрационный ответ в историю аккаунта не переносится.

## Рассказчик без внешней сети

Happy Path использует настоящий `OfflineProvider`: демонстрационный ответ проходит сохранение через `Narrator`, `AiRequest`, `StoryTurn` и `StorySummary`. Тесты восстановления заменяют только внешний провайдер через `Rails.configuration.x.narration_provider`, оставляя настоящие контроллеры и модели. Провайдер сохраняет входной контекст и управляемо возвращает ответ или выбрасывает исключение. В `teardown` прежняя конфигурация восстанавливается, в том числе после падения проверки. Ключи API и интернет не нужны.

## Как читать и объяснять тесты

- `get`, `post`, `patch`, `delete` отправляют запрос приложению. `as: :json` задаёт JSON-путь, обычные `params` используются для HTML-формы.
- `assert_response` проверяет код: 200 — успех, 422 — неверные данные, 409 — конфликт состояния, 502 — ошибка рассказчика, 303 — переход после формы. Некоторые защитные редиректы приложения используют 302; `assert_redirected_to` дополнительно проверяет адрес.
- `follow_redirect!` выполняет следующий GET, чтобы проверить именно страницу, которую увидит пользователь после отправки формы.
- `assert_select` ищет элементы и текст в HTML: сообщение об ошибке, поле формы, ссылку, сохранённую команду или строку статистики.
- `assert_difference` проверяет, что появились нужные записи, а `assert_no_difference` — что отклонённый запрос не создал лишние сущности. Снимки атрибутов и `reload` проверяют изменение/сохранность уже существующих данных, а не только их количество.
- Проверки после исправления ошибки доказывают восстановление сценария: форма/сессия не остаются в нерабочем состоянии.
- Подготовка через `create_game_user`, `start_game_session!`, `complete_action` используется, когда нужно быстро получить конкретную ветку (например, чужую завершённую игру). В основном Happy Path регистрация, начало и команды выполняются именно через HTTP.

Пример для защиты: открыть `GameLifecycleBranchesTest`, тест `restart can be abandoned ...`; показать подготовку завершённой и активной игр, отсутствие изменений после GET подтверждения, удаление всех дочерних записей после POST, сохранность архива и отказ повторно обработать старое подтверждение. Это показывает сразу успешную ветку и два отклонения от неё.

## Границы проверки

Это интеграционные HTTP-тесты, которые не запускают браузер и JavaScript. Они проверяют наличие и адреса форм, диалогов и элементов настроек в HTML, но не нажатия на плавающее меню и подтверждение, `fetch`, постепенную печать, сохранение черновика/настроек в Web Storage, звук и мобильную геометрию. Для этих действий нужны отдельные браузерные system tests; задача `test:system` пока остаётся заготовкой. Также здесь нет реального ИИ, генерации картинок или проверки конкурентных запросов из нескольких процессов.

Не заявляется покрытие всех инфраструктурных исключений: блокировки/тайм-ауты SQLite, удаление записи другим процессом между запросами, сбои диска или транзакций. Обработчики `rescue` таких исключений в контроллерах не все принудительно вызываются этим набором. CSRF-защита в стандартной test-среде отключена; прохождение HTML-формы не является проверкой реального отказа по неверному CSRF-токену. Экранирование проверено на серверном HTML; безопасность вставки JSON-ответа средствами JavaScript требует браузерной проверки.

Таким образом, документ даёт карту проверенных HTTP-веток текущего прототипа. Количество assertions не используется как процент покрытия: метрика покрытия строк/ветвей отдельным инструментом здесь не измеряется.
