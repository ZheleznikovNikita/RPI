# HP и стамина как последствия сюжета

Рассказчик получает `player_stats: {"health":100,"stamina":100}` вместе с начальной сценой, памятью и последними ходами. При подготовке каждого следующего запроса читаются актуальные значения из БД. Модель оценивает последствия в контексте истории, а не по поиску слов «бой» или «бежать» в команде.

Пример ответа Polza:

```json
{
  "possible": true,
  "narration": "Стрела задела плечо, но вы успели скрыться за стеной.",
  "summary": "Герой ранен в плечо и укрылся за стеной от стрелков.",
  "health_delta": -12,
  "stamina_delta": -15,
  "requires_exertion": true
}
```

При исходных 100/100 сервер сохранит 88 HP и 85 STA. Следующая команда бежать может дать `0/-10`, после чего будет 88/75. Отдых или лечение могут восстановить показатели, если это следует из рассказа. Обычный разговор/осмотр обычно даёт 0/0; само начало боя не должно автоматически наносить урон.

## Проверка и сохранение

- Polza обязана вернуть оба изменения как целые числа. Строки, дроби, `null`, пропущенные поля и превышение пределов отклоняются. Допустимо HP: от −30 до +20 за ход; STA: от −40 до +30.
- При `possible=false` допустимые числовые изменения принудительно заменяются нулями: невозможная команда не лечит и не ранит игрока.
- `Narrator` проверяет ответ до сохранения успешного запроса. `PlayerAction.complete!` повторно проверяет сохранённые изменения и применяет их под блокировкой сессии в одной транзакции с ходом и памятью. При ошибке транзакция откатывается.
- Итоговые значения ограничены 0–100. Например, урон 15 при 8 HP даст 0, лечение 20 при 95 HP даст 100. Повторное выполнение задачи/применение того же ответа не меняет показатели второй раз.
- Изменения хранятся в JSON `AiRequest.response_payload`, сами показатели — в существующих полях `GameSession.health/stamina`. Миграция не нужна. Восстановление после сбоя применяет сохранённый ответ без повторного платного запроса, вместе с характеристиками.
- Старые сохранённые ответы и внутренние адаптеры без обоих полей трактуются как 0/0. Если передано только одно поле, ответ некорректен. Старые прохождения не пересчитываются задним числом.

## Игровые ограничения

Системные инструкции требуют соотносить урон и затраты сил с описанными событиями и учитывать остаток сил. При нуле HP сервер завершает сессию в той же транзакции, сохраняет последний ход и дату завершения. Turbo Stream переводит игровые вкладки на статистику с `from=finished_game`; кнопка назад ведёт в главное меню. Обновление страницы и восстановление пропущенного события также ведут к статистике. Следующие команды не запускают новую сессию автоматически: новую игру нужно начать из меню.

Поле `requires_exertion` обязательно в ответе Polza. Оно классифицирует попытку: бег, силовой удар, прыжок и перенос тяжестей требуют усилия, разговор/осмотр/отдых обычно нет. При исходной STA=0 и `requires_exertion=true` сервер принудительно заменяет даже заявленный моделью успех на «Действие невозможно… сначала нужно отдохнуть», сохраняет прежнюю память и нулевые изменения. Отдых при STA=0 остаётся доступен и может восстановить силы. Семантику действия классифицирует модель: сервер гарантирует правило по полученной классификации, типы, диапазоны и атомарность, но не может доказать правдоподобность каждого текста или распознать любое скрытое силовое действие, ошибочно классифицированное моделью как спокойное.

Инвентарь не меняется. Без подключения нейросети демонстрационный адаптер оставляет показатели прежними; это не полноценный локальный симулятор боя.

## Живые обновления и запуск

После принятия хода существующая рассылка Turbo Stream через Action Cable передаёт сохранённые HP/STA. `live_game.js` обновляет числа и ширину полосок во всех игровых вкладках пользователя. После перезагрузки страницы значения читаются из БД.

Чтобы применить новый контракт к настоящему API, перезапустите Rails с настроенным ключом в том же PowerShell. JSON в консоль вводить не нужно: параметры состояния и правила отправляются автоматически с каждым запросом. Старый уже запущенный production-процесс новый код не подхватит.

## Автотесты

- `test/services/storytelling/stat_changes_test.rb`: допустимые границы, совместимость со старыми ответами, неверные типы и неполные изменения.
- `test/services/storytelling/deepseek_provider_test.rb`: перенос изменений из JSON Polza, обязательность полей, отказ без изменения характеристик.
- `test/models/player_action_test.rb`: откат при неверной памяти, ограничение итоговых значений 0–100, повторное применение ответа.
- `test/integration/player_stats_test.rb`: бой → побег → восстановление, актуальные HP/STA в следующем запросе, сохранение/повторное открытие, дубликат задачи, ошибка и повтор, восстановление прерванного принятия ответа без нового обращения к API, характеристики в Turbo Stream.
- `test/system/live_game_test.rb`: после хода числа и ширина полосок обновляются в двух вкладках настоящего браузера; обнуление HP переводит обе вкладки на статистику.

Внешний API заменяется контролируемыми ответами; настоящий ключ и платные генерации для тестов не нужны. Серверный и браузерный наборы запускаются последовательно (`ruby bin/rails test`, затем `ruby bin/rails test:system`), поскольку используют общую тестовую SQLite.
